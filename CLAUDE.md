# Food

## Что это

Монорепозиторий ресторанной платформы: четыре приложения и одна дизайн-система на всех,
связанные правилом parity.

1. **Гость** (`apps/guest`) — QR-меню: сканирует код за столом, выбирает блюда, оформляет заказ.
   Единственное приложение, полностью проходимое от начала до конца.
2. **Официант** (`apps/waiter`) — смена по расписанию, зал со статусами столов, состав заказа
   по гостям, приём заказа за столом, центр сообщений и кабинет с чаевыми, целями и рангом.
3. **Кухня** (`apps/kitchen`) — доска тикетов на планшете или мониторе, вход по логину.
4. **Панель ресторана** (`apps/admin`) — менеджерская: сотрудники и их учётные записи.
   Ровно один раздел: она появилась потому, что кому-то надо заводить входы официантам и поварам.
5. **Дизайн-система** (`packages/ui`) — React-компоненты и Figma-компоненты, зеркальные 1:1.
   Токены, стили и компоненты существуют в обеих средах одновременно.

Приложения делят ДС, домен и вход через `packages/*` — иначе parity с Figma рассыплется
на четыре расходящиеся копии.

**Бэкенд — Supabase**, проект `Food` (`rkuyxugalgkgunofrdkh`, регион ap-south-1, план free).
Все приложения ходят в одну базу через `packages/api`; локальных моков больше нет.
Плюс edge-функция `staff-admin` — заведение учётных записей персонала.
Цикл замкнут: гость оформил заказ → тикет на кухне → повар отметил готовым → у официанта стол
загорелся «Ждут подачу» → отдал → «Занят».

## Текущее состояние

**Работает:** главная стола (хаб после скана QR) → меню (категории + поиск) → карточка блюда
(у пиццы выбор размера и теста) → корзина (подача, комментарий кухне, допродажа, деление счёта) →
«Оформить заказ» → подтверждение заказа. С главной также доступны «Мои заказы», счёт за стол с чаевыми
и вызов официанта с поводом — локальные моки. Данные — локальный мок, бэкенда нет.

**Дизайн-система:** 24 React-компонента и 27 иконок. Ноль хардкода — каждый цвет/отступ/радиус
через CSS-переменную, каждый текст через Text Style. В Figma зеркалировано всё, кроме кухни:
`TicketCard`, иконка `Undo` и экран доски ещё не перенесены — это единственный открытый долг
синхронизации, он записан в `artifacts/parity-report.md`. Там же грабли Plugin API, на которые
напоролись при прошлых прогонах, — читать перед следующим.

**Валюта:** таджикский сомони, формат «55 с.». Форматирование — только через `formatPrice()`
из `packages/domain/src/format.ts`. Внутри неразрывный пробел (`Intl`) у четырёхзначных сумм — это ломает
поиск подстроки вида `'1 240'` в тестах, искать по индексу, а не по тексту.

**Цены — рынок Душанбе.** Горячее 50–60 с., салаты 35–48 с., супы 28–55 с., пицца 60–100 с.
в зависимости от размера, десерты 30–32 с., напитки 18–20 с. Средний чек на двоих выходит
150–200 с. Если правите цены — держите этот порядок: пресеты чаевых и шаг их округления
(`tipFromPercent` в `BillPage`) рассчитаны на трёхзначный счёт.

## Ключевые архитектурные решения

**Репозиторий — шов между экраном и данными.** Экраны не знают, откуда данные: `menuRepository`
у гостя и `floorRepository` у официанта тонко оборачивают `@food/api`, а хелперы цены/меты/опций
живут рядом. Переезд с локальных моков на Supabase не изменил ни одного экрана — ради этого шов
и заводился. В `floorRepository` осталось единственное, чего нет в базе: расписание смены.

**Ключ строки корзины — составной.** `cartKey(dishId, selections, removed, extras)` из домена:
пицца 21 см и 25 см — две разные строки корзины, бургер «без лука» и обычный — тоже. `CartItem.key` — это то, по чему
корзина различает позиции, `dishId` — только ссылка на блюдо.

**Опции блюда.** `DishOptionGroup` с `layout: 'detailed' | 'simple'`. `detailed` — размер
(есть `caption` и `price`, выбранная цена **заменяет** базовую через `resolveDishPrice`),
`simple` — тесто (только `label`, на цену не влияет). Пока только single-select;
модификаторы-чекбоксы из фазы 2 потребуют третьего layout.

**Стол из URL, дальше — сессия вкладки.** `?table=7` → «Стол 7 · основной зал». Нет параметра —
дефолт «12». Читаем URL **один раз** и держим в `sessionStorage`: `useSearchParams` привязан к текущему
location, а внутренние переходы query не переносят — иначе стол схлопывался бы в дефолт после первого же
перехода с главной, и счёт выписывался бы на чужой стол. Повторный скан QR с `?table=` в той же вкладке
стол меняет; карандаш на главной позволяет исправить номер вручную. В localStorage по-прежнему **не**
ходим: запомненный чужой стол из прошлого визита хуже дефолта. `TableSessionProvider` обязан быть
**внутри** `<HashRouter>` — ему нужен роутер-контекст для `useSearchParams`.

**Главная — хаб, каталог на `/menu`.** QR ведёт на `/` (`HomePage`), меню живёт на `/menu`. Все возвраты
«в меню» из корзины и блюда ведут на `/menu`, кнопка «назад» в меню — на главную. Плитки чаевых и отзыва
намеренно `disabled` с бейджем «скоро» — так помечено на блок-схеме продукта.

**Заказы сессии живут в базе, а не в памяти вкладки.** `OrdersProvider` читает заказы стола из
Supabase и подписан на realtime: повар отметил блюдо готовым — строка в «Моих заказах» меняется
сама. Статус настоящий (`orderStatusLabel`), у каждой тарелки свой: одну уже несут, другая ещё
в очереди. Просьба счёта — пока локальное подтверждение на 30 секунд.

**Гостю статус переводится, а не пересказывается.** `ready` для кухни — «готово», для гостя —
«Уже несут»: он ждёт тарелку, а не команду повару. Цветом выделено только это состояние,
остальное читается текстом.

**Позиции заказа гость читает из самого заказа.** `SessionOrderItem` несёт название и цену снимком
на момент оформления — искать блюдо в каталоге по строке заказа нельзя: его могли переименовать
или снять с продажи. До этой правки экран «Мои заказы» искал блюда в меню по id строки заказа
и не показывал ни одной позиции.

**Вызов официанта — настоящее сообщение, а не заглушка.** Поводы чипами плюс поле «Написать
официанту»: строка уходит в `waiter_calls` (`reasons` — выбор из списка, `message` — слова гостя)
и realtime всплывает у официанта в «Сообщениях» с бейджем на вкладке. Разные колонки потому,
что поводы можно считать и группировать, а сообщение нужно прочитать целиком — и на экране
официанта оно набрано крупнее поводов. Подтверждение у гостя держится 30 секунд: он должен
увидеть, что просьба ушла, но висеть весь визит ей незачем.

**Статусы стола двигает база, а не приложения.** Триггеры `orders_sync_table_status` и
`orders_occupy_table`: новый заказ занимает стол, `ready` зажигает «Ждут подачу», `served`
возвращает «Занят», `paid` освобождает — но только когда закрыт весь счёт стола, а не один
заказ из трёх. Если бы это чинило каждое приложение само, три реализации разошлись бы
на первой же гонке.

**Названия и цены копируются в заказ.** `order_items.title` и `unit_price` — снимок на момент
оформления: переименовали блюдо или сменили цену — старый счёт и тикет на кухне не должны
измениться задним числом.

**RLS включён, но политики пока демонстрационные.** Авторизации нет, все три приложения ходят
с публикуемым ключом, поэтому анониму разрешены правки заказов и столов. Перед реальными данными
завести Supabase Auth для персонала — гостевое меню публичное по природе, приложения персонала нет.

**Строка `select` в supabase-js обязана быть литералом.** Склейка через `+` превращает её
в обычный `string`, и типы встроенных выборок схлопываются в `GenericStringError`.

**Имя канала realtime — уникальное на подписку** (`channelName()` из `packages/api/src/client.ts`).
Одно имя на два компонента — и второй `.on()` прилетает уже после `subscribe()`: supabase-js бросает
исключение, React роняет экран в белое. Так и вышло, когда на запросы гостей подписались сразу
оболочка (ради счётчика на вкладке) и сам экран сообщений.

**Таблицу в realtime мало добавить в код — нужна публикация.** Забытая `waiter_calls`
в `supabase_realtime` роняла весь канал официанта с `TIMED_OUT`: одна неудачная привязка
обрывает join целиком.

**Стоп-лист — `available: false` у блюда.** Витрина показывает «Нет в наличии» вместо кнопки, строка
корзины — вместо счётчика кнопку «Убрать». Закончившееся блюдо **не входит** в `totalPrice` и не
уезжает в заказ: единственный источник оплачиваемых позиций — `cart.payableItems`, чекаут блокируется,
пока стоп-лист в корзине. Гость сам решает, чем заменить, — молча выкидывать его позицию нельзя.

**Деление счёта считается на клиенте.** `data/split.ts` → `splitTotals()`: режим `equal` делит всё
поровну, `items` отдаёт назначенные позиции своему гостю, а неназначенные считает общими. Остаток от
деления раскидывается по 1 с на первых гостей, иначе сумма долей не сходится с итогом. Бэкенд для
этого не нужен: делить нечего, кроме уже известных сумм, — раскладку гость показывает официанту.
На `/bill` тот же хелпер агрегирует раскладку по всем заказам сессии (ключи префиксуются номером
заказа, иначе одинаковые строки из разных заказов схлопнулись бы), чаевые идут общей строкой.

**Оформление живёт в корзине, отдельного чекаута нет.** Гость сидит за столом: адрес, способ
получения и оплата — вопросы курьерской модели, а не dine-in. Кнопка в корзине отправляет заказ
и ведёт сразу на «Заказ принят»; экран `CheckoutPage` и типы `DeliveryMethod`/`PaymentMethod`
удалены, а не спрятаны — иначе они переживут ещё три итерации.

**Пожелания кухне живут в корзине, а не в чекауте.** `servingMode` («по мере готовности» / «вместе»)
и комментарий — это разговор с кухней, поэтому они рядом с блюдами; в чекауте комментарий был про
курьера. Хранятся в `CartProvider` (`qr-menu.cart-prefs`) и снимаются в `SessionOrder` при оформлении.

**Закрытый счёт — это конец визита, а не «оплачено».** Платёжного шлюза нет (фаза 4), поэтому
`paid` означает «официант забрал деньги и отпустил стол». Такие заказы уходят и из состава стола
у официанта, и из «Моих заказов» гостя: за столом уже другие люди. Список статусов держит
check-ограничение в базе — опечатка в коде иначе тихо создаст заказ в несуществующем статусе.

**Объединение столов — ссылка второго стола на первый.** `dining_tables.merged_into`: счёт и
заказы живут на главном столе, второй уходит из ленты зала и его номер показывается на карточке
главного («Со столом №7»), а вместимость складывается. Отдельная таблица «группы столов»
понадобилась бы ради того же одного поля. Разъединение возвращает стол в зал, но заказы остаются
на главном: делить общий счёт обратно нечем — кто за каким столом сидел, база не знает.

**Пересадка и объединение считают статусы стола заново.** Обычные триггеры ловят смену статуса
заказа, а тут у заказа меняется стол — поэтому `refresh_table_status()` пересчитывает статус
по заказам стола. Бронь при этом не сбивается: она стоит на будущее, а не на сейчас.

**Бронь — строка в `reservations` плюс отметка в столе.** Гость брони (имя, телефон, персон)
живёт в своей таблице, а время дублируется в `dining_tables.reserved_at` намеренно: зал читается
одним запросом, без join к броням на каждую плитку. Снятая бронь не удаляется, а помечается
`cancelled_at` — по отменам видно, как часто столы простаивают зря. Бронировать можно только
свободный стол: за занятым уже сидят.

**Карточка занятого стола отвечает на вопросы ТЗ фактами визита.** Время посадки — первый заказ
визита, гости — `orders.guests`, позиции — сумма количеств. Всё считается в `fetchFloor` из тех же
сегодняшних незакрытых заказов, что и статус: отдельной сущности «визит» в базе нет, и заводить её
ради трёх чисел не за чем.

**Просьбы гостей висят и в «Сообщениях», и у карточки стола.** Это одна лента `waiter_calls`,
показанная там, где официант стоит: в зале — рядом со столом, в разделе — списком за смену.
Кнопка «Выполнить» одна и та же.

**Подачу двигает заказ, а не рука официанта.** Кнопка «Отдал гостям» переводит готовые заказы
стола в `served`, а «Занят» возвращает триггер. Если бы экран правил статус стола напрямую,
появилась бы вторая правда о том, что происходит за столом. Показывается кнопка по составу
(есть позиция «Нужно подать»), а не по цвету стола: статус стола может отстать.

**Смена — запись в базе, а не флажок в памяти вкладки.** `shifts` держит расписание (`starts_at`,
`ends_at`) и факт (`started_at`, `ended_at`): официант мог опоздать, и это разные вещи. Кнопка есть
и на главной, и в кабинете, но правда одна — строка смены. Приём заказа смена по-прежнему не
блокирует: запирать работу на расписании значит останавливать зал из-за опоздания менеджера
с графиком.

**Ранг считается, а не хранится.** `RANKS` в домене (`Новичок 3%` → `Легенда 12%`), порог берётся
от суммы принятых заказов официанта. Хранить ранг колонкой значит завести второй источник правды,
который разойдётся с заказами на первом же перерасчёте. Пороги считаны от душанбинского чека:
«Умелый» — это пара десятков столов, а не год стажа.

**Цели считаются от чаевых за всё время.** «Накопить на студию» — это про личные деньги официанта,
а не про выручку ресторана, поэтому прогресс идёт от `orders.tip` его заказов. Вывод на карту
остаётся выключенным: платёжного шлюза нет (фаза 4).

**Статус стола — четыре значения, не больше.** `TableStatus` из `packages/domain/src/floor.ts`:
`free` / `busy` / `attention` / `reserved`. Цвета живут в токенах `--color-status-*`, а не в экранах:
иначе «свободен» позеленеет по-разному в приложениях официанта, кухни и админки. Промежуточных
оттенков не заводим — официанту нужно с одного взгляда отличить «можно сажать» от «зовут».

**Вход сотрудника — один на все приложения персонала.** `packages/staff` держит `AuthProvider`,
`useAuth` и экран входа; официант, кухня и админка подключают их, а не пишут свои. На кухне вход
один раз при запуске планшета — сессию хранит Supabase, а выход спрятан мелкой строкой в шапке:
это стена, случайный тап по «выйти» стоит дорого. Гостевое меню
сюда не ходит совсем: оно публичное по природе, входить там некому.

**Учётные записи заводит edge-функция, а не браузер.** Создание пользователя требует
service_role-ключа — в клиентском приложении ему не место ни при каких условиях. Поэтому
`supabase/functions/staff-admin` проверяет по токену, что вызывает менеджер, и только тогда
создаёт пользователя и строку в `staff`. Проверка роли на клиенте осталась бы украшением:
запрос к функции можно послать и мимо интерфейса.

**Сотрудник = строка `staff` + пользователь Auth.** Связывает их `staff.auth_user_id`. Вход без
строки в штате — это `stranger`: пускать такого в приложение персонала нельзя, а молчать о причине
нельзя тем более, поэтому у него свой экран с объяснением.

**RLS: править заказы может только персонал, гость — только чаевые.** Зал, вызовы и заказы правит
вошедший сотрудник (`is_staff()`). Гостю оставлена ровно одна колонка: политика для `anon` разрешает
строку, а «менять можно только `tip`» выражено грантом на колонку — этого RLS не умеет, она видит
строку целиком. Проверяется одной командой: `PATCH orders {"status":...}` анонимом отдаёт 401,
`{"tip":5}` — 204.

**«Рекомендуемые блюда» — это высокий рейтинг, а не персонализация.** Движка рекомендаций нет,
выдумывать его нечестно, поэтому полка показывает блюда с рейтингом от 4.7 и прячется, как только
официант начал искать: он уже знает, что ему нужно.

**Ориентировочное время готовки считается грубо и честно.** Нормативов у блюд нет, поэтому
`estimateCookMinutes` берёт базовые 15 минут или самый поздний курс подачи, если официант их
назначил. Обещать точнее, чем знаем, нельзя — гость запомнит цифру.

**Приём заказа — отдельная ветка маршрутов без таб-бара.** `/table/:tableId/…`: гости → меню →
блюдо → черновик → «заказ на кухне». Официант ведёт один разговор с гостем, и выйти из него
посреди набора можно только осознанно, кнопкой назад, — таб-бар в этот момент только мешает.

**Дозаказ доезжает в открытый заказ стола, а не заводит второй.** Черновик перед отправкой
спрашивает базу, есть ли у стола незакрытый заказ, и по умолчанию дописывает позиции в него:
повару нужен один тикет на стол, а не два одинаковых. Переключатель «Отдельным тикетом» рядом —
бывает, что дозаказ идёт другой компании за тем же столом. Статус пересчитает триггер: пока новые
позиции в очереди, заказ снова «в работе», даже если прошлые блюда уже поданы.

**Поданное с кухонной доски уходит.** При дозаказе в тот же заказ повар должен видеть, что
осталось приготовить, а не историю визита, поэтому позиции в статусе `served` в тикет не попадают.

**Черновик заказа живёт в sessionStorage, а не в базе.** Пока заказ набирается, он никому,
кроме официанта, не нужен: кухне рано, счёту рано. Перезагрузка вкладки его переживает, смена — нет
(`sessionStorage`, не `localStorage`): забытый вчерашний черновик хуже пустого экрана, его отправят
на кухню не глядя.

**Гость и время подачи — свойства позиции.** `order_items.guest_index` (null — общее блюдо) и
`serve_after_minutes` (null — по готовности). Поэтому у заказа, принятого официантом, состав
раскладывается по гостям точно; догадка по слагу блюда осталась только для гостевых заказов
с раскладкой счёта.

**Состав блюда и «убрать ингредиент» — один список.** Убрать можно только то, что в блюде и так
есть, поэтому у гостя состав нарисован переключателями: выключил — значит, без него. Отдельного
списка «что можно убрать» не заводим, он был бы копией состава.

**Модификаторы: убрать — из состава, добавить — из `dish_extras`.** Убрать можно только то, что уже
лежит в `dishes.ingredients`, поэтому отдельной таблицы «что убрать» не нужно. Добавки — своя
таблица с надбавкой к цене; в отличие от опции размера, она цену **прибавляет**, а не заменяет.
Снимок обоих списков едет в `order_items.modifiers` строкой «без лука · + сыр чеддер».

**Перетаскивание блюда к гостю — за ручку, а не за строку.** Механика та же, что на кухонной доске
(pointer-события, порог 8 px, копия в портале), но `touch-action: none` стоит только на ручке:
иначе список гостей нельзя было бы прокрутить пальцем. Куда упадёт тарелка, ищем через
`elementFromPoint` — группы прокручиваются, и заранее посчитанные координаты врут.

**Состав заказа официант видит по гостям.** `groupItemsByGuest` из
`packages/domain/src/service.ts` раскладывает позиции стола по раскладке счёта, сделанной гостем:
что никому не закреплено — отдельная группа «Общие позиции», а не выдуманная доля. Официант несёт
тарелку конкретному человеку, и доля от общего блюда на вопрос «кому» не отвечает — деньги делит
`splitTotals`, это другая задача.

**Статус живёт на тарелке, а статус заказа из него выводится.** `order_items.status`
(`queued/cooking/ready/served`) двигают повар и официант, а `orders.status` пересчитывает триггер
`order_items_sync_order_status`: заказ готов, когда нести можно всё; в работе, пока хоть что-то
начато. Обратной записи нет — иначе у одного факта появились бы два источника, и они разошлись бы
на первой же полуготовой тарелке. `paid` и `cancelled` триггер не трогает: это решения не кухни.

**На кухне тап по позиции отмечает её готовой, а не весь тикет.** Готовая строка гаснет,
зачёркивается и получает зелёную галочку вместо количества; тикет уезжает в «Готово» сам, когда
готово всё. Кнопка на тикете осталась — она двигает разом все позиции. У официанта та же логика
с другой стороны: «Подал» на строке закрывает одну тарелку, «Отдал гостям» — все готовые сразу.

**Гостя у позиции приходится угадывать по слагу блюда.** Раскладка хранится ключами строк корзины
(`d-13|g-size:o-25`), а в `order_items` этого ключа нет — есть блюдо и текст выбора. Сопоставляем по
слагу и «съедаем» ключ, чтобы вторая такая же позиция досталась следующему гостю; два разных размера
одной пиццы у разных гостей могут поменяться местами. Точным это станет, когда ключ строки поедет
в `order_items`.

**Состав стола — только сегодняшние заказы.** Признака «визит» в базе нет, поэтому вчерашний заказ
за тем же столом к нынешним гостям не относится и на экран не попадает.

**Цвет тикета — стадия, а не возраст.** `--color-ticket-new` (красный) / `-cooking` (жёлтый) /
`-ready` (зелёный): повар видит колонку цветом, даже глядя вскользь. На жёлтой шапке текст тёмный —
белый по жёлтому не читается.

**Возраст при этом не потерян:** просроченный тикет получает тёмную плашку таймера
(`neutral/ink`) — единственный цвет, читаемый и на красном, и на жёлтом, и на зелёном. Пороги
лежат в `DEFAULT_AGE_THRESHOLDS` (8 и 15 минут) и `READY_AGE_THRESHOLDS` (3 и 6): готовое блюдо
стынет быстрее, чем ждёт неготовое.

**Кухня — канбан из трёх колонок.** «Новый → Готовится → Готово» — это ровно `TicketStatus`
из домена, а не отдельная сущность экрана. Тикет двигают перетаскиванием или кнопкой — кнопка осталась как надёжный путь
для мокрых рук. Перетаскивание на pointer-событиях, а не на HTML5 drag-and-drop: последний мышиный
и на планшете не работает вовсе. `touch-action: pan-y` оставляет вертикальный свайп колонке,
горизонтальный забирает под перенос; порог 8 px и условие |dx| > |dy| отделяют жест от скролла.
Карточка под пальцем рисуется в портале поверх страницы — внутри колонки её резал `overflow`. В «Готово» тикет ждёт официанта — оттуда
его либо «Выдано» (уходит с доски), либо «Вернуть» (обратно в работу, если блюдо вернули).

**В колонке «Готово» таймер считает остывание, а не готовку.** Отсчёт идёт от `readyAt`, пороги
втрое короче (`READY_AGE_THRESHOLDS`, 3 и 6 минут): пять минут на раздаче — уже холодная тарелка.

**Кухонный экран читается с трёх метров.** Позиции набраны `body-l`, номер стола и таймер —
`heading-8`; `body-s` там, где повар не читает, а опознаёт. Один таймер на весь экран
(`useNow`), а не по секундомеру в каждой карточке.

**Оплату подтверждает сервер, а не браузер.** Мок-шлюз (`supabase/functions/mock-pay`) закрывает
счёт сам: у гостя в RLS есть право ровно на одну колонку — чаевые, и «оплачено» он объявить не
может. Когда появится настоящий шлюз, в функции появится проверка его подписи, а всё остальное
останется как есть. Сумму она считает по базе после записи чаевых: гость мог оставить их раньше,
отдельным действием, и клиент об этом уже не помнит.

**Отказ платежа подмешивается нарочно.** Один раз из пяти мок отвечает отказом — путь
«не прошло → повторить» должен быть проверен, а не нарисован. Экран обработки живёт полторы
секунды: мгновенный мок не показал бы того, ради чего он нужен.

**Чаевые вместо платежа.** Платёжного шлюза нет (фаза 4), поэтому чаевые не оплачиваются отдельно,
а прибавляются к счёту стола: `tip` лежит в том же `OrdersProvider` (`qr-menu.tip`), `billTotal =
sessionTotal + tip`, и «Попросить счёт у официанта» несёт итог уже с ними. Пресеты процентов собраны
на существующем `OptionGroup layout="detailed"` — новых компонентов чаевые не потребовали. Округление
пресета: шаг 10 с до 1 000 с, дальше 100 с — «1 757 с» читается как ошибка расчёта, а грубая сотня
на маленьком счёте превращает 10 % в 8 %.

**Сервис-воркер кэширует свою статику и только её.** Запросы в Supabase проходят мимо кэша:
заказ и его статусы обязаны быть свежими, а показать вчерашний счёт из кэша хуже, чем честно
не показать ничего. Оболочка отдаётся из кэша только когда сети нет — сначала сеть, кэш запасным.
В разработке воркер не регистрируется: он прятал бы правки за старой версией.

**HashRouter, не BrowserRouter.** Приложение раздаётся как статика без серверных rewrite.
Поэтому URL вида `/#/?table=7` — query идёт после хэша.

## Правила parity

React-компонент = Figma-компонент = токен. Расхождение — баг, чинится с обеих сторон.

| Сущность | React | Figma |
|---|---|---|
| Цвет | CSS var `--color-*` | Variable `Colors/*` |
| Шрифт | класс `.ts-*` из `typography.css` | Text Style с тем же именем |
| Spacing / Radius | `--space-*` / `--radius-*` | Variable `Spacing/*` / `Radius/*` |
| Тень | `--shadow-*` | Effect Style `Shadow/*` |
| Компонент | `<Button variant="main"/>` | Component Set `Button`, свойство `Variant=Main` |

- Никакого хардкода цветов/размеров/шрифтов вне `tokens.*`.
- Имена 1:1. Figma-свойства в TitleCase (`Variant`), React-пропы в camelCase (`variant`) —
  это единственное согласованное расхождение.
- Новый компонент зеркалится сразу, долги синхронизации не копим.
- После значимой итерации — обновить `artifacts/parity-report.md`.

## Команды

Всё из корня воркспейса, `npm install` — один раз на весь монорепозиторий.

```bash
npm install            # поставить зависимости всех приложений и пакетов
npm run dev            # гостевое меню, порт 5173 (host:true — видно с телефона в той же Wi-Fi)
npm run dev:waiter     # приложение официанта, порт 5174
npm run dev:kitchen    # экран кухни, порт 5175
npm run dev:admin      # панель ресторана, порт 5176
npm run typecheck      # tsc -b по всем воркспейсам
npm run lint           # oxlint по apps и packages
npm run build          # сборка всех приложений
```

Деплой: `git push origin main` → Vercel собирает автоматически. На каждое приложение свой проект
со своим Root Directory (`apps/guest`, `apps/waiter`); проект для кухни ещё не заведён.

## Известные ограничения данных

- 5 фотографий растянуты на 14 блюд — у чизкейка фото бургера. Ждёт реальных фото.
- Нет налогов и сервисного сбора.
- Расписание смен заполнено демо-данными на неделю вперёд; интерфейса для менеджера, чтобы его
  править, пока нет — только SQL или панель ресторана в будущем.
